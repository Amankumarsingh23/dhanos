## 3. Recommended implementation order

Sequenced so each phase is independently useful and later phases depend on earlier data existing, rather than building UI for data that can't exist yet:

1. **Foundation**: repo scaffold (Next.js + TypeScript + pnpm) ✅, environment variable setup ✅, base layout shell ✅, household + membership model with RLS (roles, status, idempotent creation) ✅, auth (sign up/in/out, verification, password reset, protected routes, onboarding that creates both the profile and the household, `profiles` table) ✅, authenticated app shell (navigation, mobile nav, privacy mode) ✅ — remaining: a real (hosted) Supabase project for staging/production, and a collaboration-invite flow to actually add a second person to an existing household.
2. **Core ledger**: institutions, accounts, transactions (income/expense/transfer discriminated), income sources, recurring commitments. Schema complete (`people`, `institutions`, `financial_accounts`, `account_balance_snapshots`, `transaction_categories`, `transactions`, `transaction_splits`, `recurring_rules`, `attachments`, `activity_events`, `income_sources` — see [database-plan.md](./database-plan.md), [financial-domain-model.md](./financial-domain-model.md)). **People, Institutions, Accounts, Categories, Transactions, Income, and Expenses now have full CRUD/analysis UI** (`/app/people`, `/app/institutions` — PROMPT 8; `/app/accounts` — PROMPT 9; `/app/cash-flow` + `/app/cash-flow/categories` — PROMPT 10; `/app/income` — PROMPT 11; `/app/expenses` — PROMPT 12), built first per this phase's own ordering since loans/policies/investments will all reference them. Recurring commitments (`recurring_rules`) still has no dedicated management UI or generation job — the Expenses feature can create a minimal rule when an expense is marked recurring, but nothing lets a household view, edit, or generate future occurrences from one yet.
3. **Net worth foundation**: assets (movable/immovable) ✅ (PROMPT 27/28), liabilities ✅ (PROMPT 24), valuation snapshots ✅ (`asset_valuation_snapshots`, PROMPT 27), net-worth snapshot rollup ✅ (PROMPT 32 — see the Net-worth engine row in section 1). **Deviation from this document's own recommended order**: this phase was originally meant to come *before* investments/debt/protection (phases 4–6), since a net-worth rollup needs something to sum even in minimal form — instead it was built last, well after every module it rolls up already existed independently. This turned out fine in practice: PROMPT 32's rollup was able to reuse every other module's own already-correct outstanding/valuation/ownership logic directly (loans' `getDebtSummary`, lending's `computeLendingTotals`, assets' `computeNetWorthContributionMinorUnits`, liabilities' certainty split) rather than needing any of them to change shape to accommodate it — the "teach a future rollup to read this" notes left in phases 4–6 below turned out to require no actual rework.
4. **Investing**: `investment_accounts`/`investment_assets`/`investment_holdings`/`investment_transactions`/`investment_valuation_snapshots`/`investment_documents` schema ✅ (PROMPT 16 — see [database-plan.md](./database-plan.md) §3, [financial-domain-model.md](./financial-domain-model.md) §4); SIPs ✅ (PROMPT 17), portfolio/performance reporting ✅ (PROMPT 18), and dedicated staking-position/daily-value tracking ✅ (PROMPT 19) all built — see the rows in section 1 above. **Deviation from this document's own recommended order**: PROMPT 16 asked for the investment domain directly, before phase 3 (net-worth foundation) existed — the investment tables were built without assets/liabilities/net-worth-rollup underneath them yet. This turned out fine structurally (investment_holdings' valuation history stood on its own) — PROMPT 32's net-worth rollup later read investment_holdings' latest valuations directly via `getPortfolioHoldings`, exactly as anticipated, with no changes needed to the investing domain itself.
5. **Debt**: loans (with principal/interest-split payments) ✅ (PROMPT 21 — see the Loans & debt row in section 1); lending/receivables ✅ (PROMPT 23 — see the Lending & receivables row in section 1); informal borrowing and general liabilities ✅ (PROMPT 24 — see the Informal borrowing & liabilities row in section 1), all reusing the same append-only payment-history pattern loans established. **Deviation from this document's own recommended order**: PROMPT 21/23/24 asked for loans, lending, and liabilities directly, ahead of phase 3 (net worth) and phase 7 (planning) — this turned out fine, since PROMPT 32's net-worth rollup later folded all three in directly (`getDebtSummary` for institutional debt, `computeLendingTotals` for receivables, `computeOtherLiabilitiesBreakdown` splitting liabilities by source/certainty) with no changes needed to any of the three modules themselves.
6. **Protection & property depth**: insurance policies ✅ (PROMPT 25 — see the Insurance row in section 1) plus claims, structured waiting periods, and a dashboard ✅ (PROMPT 26 — see the Insurance claims & dashboard row); movable/immovable/business assets ✅ (PROMPT 27 — see the Assets row), deepened with property-specific fields, valuation confidence, and asset-linked income ✅ (PROMPT 28 — see the Property depth & asset income row). Documents: `transaction` (Expenses' receipts), `insurance_claim`, and `asset` have real upload UI — `financial_account`/`lending`/`insurance_policy` remain schema-ready only. **Deviation from this document's own recommended order**: PROMPT 25/26/27/28 asked for insurance, claims, assets, and property depth directly, ahead of phase 3 (net worth) and phase 7 (planning) — `computeNetWorthContributionMinorUnits` (src/lib/calculations/assets.ts) was already the exact per-asset figure a future rollup would sum; PROMPT 32's net-worth rollup later summed it directly (split by asset_group into movable assets and property), with no changes needed to the assets module itself. A policy's coverage amount is still not folded into net worth — insurance coverage was never part of PROMPT 32's formula (it's protection against a future loss, not a currently-owned asset).
7. **Planning**: goals ✅ (PROMPT 30 — see the Financial goals row in section 1; built on top of the Accounts and Investments modules' own balance/valuation queries rather than a new value pipeline, and reusing PROMPT 20's `goal-funding.ts` calculator directly for the future-value math); emergency-fund planning ✅ (PROMPT 31 — see the Emergency fund planner row; built the same way, on top of Expenses/Loans/Insurance's own existing queries rather than a new value pipeline); monthly financial closing ✅ (PROMPT 33 — see the Monthly financial closing row; the capstone of this phase, needing steps 2–6's data to close against, plus the net-worth engine from earlier in this same phase — sequenced last within Planning specifically because it depends on the most other modules). **Deviation**: PROMPT 29 (money drains) was also built ahead of this phase — see item 8 below, since it's an analysis layer over existing modules (recurring commitments, assets) rather than something planning itself depends on.
8. **Money drains** (PROMPT 29 — see the Money drains row in section 1): a household-entered register of depreciating and money-draining items, cross-linking to `recurring_rules` and `assets` rather than duplicating either. Not part of this document's original numbered phases (it isn't in [product-scope.md](./product-scope.md)'s module list) — sequenced here because it reads/references data every earlier phase already produces (recurring commitments from phase 2, assets from phase 6) without needing net worth or planning to exist first.
9. **Documents vault** (PROMPT 34 — see the Financial documents vault row in section 1): a household-wide document store with its own category taxonomy, expiry tracking, and archive/permanent-delete lifecycle, reusing PROMPT 9's private Storage bucket and RLS unchanged. Not part of this document's original numbered phases — sequenced here, after every module that might want to link a document to one of its records (accounts, loans, insurance, assets, goals, ...) already exists, but before the insight layer, since "documents" is explicitly named as its own line item in [product-scope.md](./product-scope.md)'s module list, unlike money drains.
10. **Reminders / financial calendar** (PROMPT 35 — see the Reminders / financial calendar row in section 1): generated occurrences of dated obligations across essentially every other module. Sequenced here, after every source module it reads from already exists (SIPs, loans, insurance, income, lending, documents, accounts, goals, assets, monthly closing) — an "insight layer" item in [product-scope.md](./product-scope.md)'s original module list, but pulled ahead of reports/decision-journal/literacy (item 11 below) since it's the one insight-layer item that needed the most other modules to be real first, not the least.
11. **Reports / reporting centre** (PROMPT 36 — see the Reports / reporting centre row in section 1): 17 reports spanning cash flow, investments, debt, protection/property, lending, planning, and net worth, sequenced last within the insight layer specifically because a report is only as good as the modules it reads from — by this point in the build, every one of them already existed. **Deviation from this document's own recommended order**: reports/reminders/decision-journal/literacy were originally meant to be one undifferentiated "insight layer" item (12 below); PROMPT 35 and PROMPT 36 split reminders and reports out and built them back-to-back instead, in the reverse of product-scope.md's own listed order (reports before reminders) — reports turned out to depend on reminders for nothing at all, so the actual build order made no structural difference, only a documentation one.
12. **Financial decision journal** (PROMPT 37 — see the Financial decision journal row in section 1): captures the reasoning behind a significant financial decision at the time it's made, immutably. Sequenced last of the three insight-layer splits (reminders, reports, decision journal) — it extends PROMPT 35's reminders (review dates) the same way reports read from every other module, so it needed both to already exist.
13. **Financial-literacy content** (PROMPT 38 — see the Money Classroom row in section 1): 18 static, source-controlled topics plus six deterministic personalized insights, each reusing an already-existing feature query/calculator (income trend, recurring rules, loans, emergency-fund plan, platform allocation, insurance overview) rather than introducing a new value pipeline. Sequenced last of the insight-layer items specifically because its personalized insights needed the most other modules (income, debt, recurring commitments, emergency fund, investments, insurance) to already exist and be independently correct — the same reasoning PROMPT 36's reports and PROMPT 37's decision journal were sequenced late for.
14. **Insight layer**: reports ✅ (PROMPT 36 — see item 11 above); projections/calculators (with assumption disclosure) ✅ (PROMPT 20 — see the Financial calculators row in section 1); reminders ✅ (PROMPT 35 — see item 10 above); financial decision journal ✅ (PROMPT 37 — see item 12 above); financial-literacy content ✅ (PROMPT 38 — see item 13 above). **Deviation from this document's own recommended order**: PROMPT 20 asked for calculators directly, ahead of reports/reminders/decision journal/literacy in this same phase and well ahead of phases 3, 5, 6, and 7 (net worth, debt, insurance/assets, goals) that a loan-prepayment or goal-funding calculator would eventually want to read real data from. Every PROMPT 20 calculator works fully standalone today (manually-entered inputs only); the three account-linked ones (lump sum, daily growth, goal funding) read an existing `financial_accounts` balance to prefill, but none of them read a real loan or goal record yet, since those modules don't exist — a future Loans/Goals module should teach those calculators to link to a real record the same way, rather than the calculators needing to change.
15. **Global search** (PROMPT 39 — see the Global search row in section 1): household-scoped search across every entity module built in phases 1–14. Sequenced last of all — the same reasoning financial-literacy content (item 13) was sequenced last of the insight layer, taken to its logical conclusion: a cross-entity search feature is only as complete as the set of entities it can search, so it necessarily waited until every one of the 16 named entity types (spanning core ledger, investing, debt, protection/property, and planning) already existed as a real, RLS-scoped table. Not part of this document's original numbered phases (it isn't in [product-scope.md](./product-scope.md)'s module list, the same "added directly" status money drains (item 8) and this item share).
16. **Settings and privacy controls** (PROMPT 40 — see the Settings row in section 1): profile/household/privacy/data preferences, and the household-scoped data export folded into this rather than its own later "platform hardening" line item. Sequenced last for the same reason global search (item 15) was — the Household section's default-goal-assumption and timezone fields, the Data section's archived-records summary, and the export all reuse (never re-derive) columns and query shapes every earlier phase already established (goals' own assumption fields, households.timezone, the same 16+ entity tables search reads from). Not part of this document's original numbered phases, same "added directly" status as money drains and global search. **Revisited directly by PROMPT 42** ("Data export, hardened" row in section 1) once every entity module named in that prompt already existed — the same "wait until the thing being read from is real" reasoning phases 3–14 above already used, applied here to hardening rather than to a first build.
17. **CSV import foundation** (PROMPT 41 — see the CSV import foundation row in section 1): explicitly sequenced only "after manual workflows are stable," per the prompt's own opening instruction — transactions (PROMPT 10), account balances (PROMPT 9's reconciliation flow), and investment valuations (PROMPT 16) all needed their manual create paths, validation rules, and category/account/holding taxonomies to already be real and correct, since the importer's resolution step (src/features/imports/resolve.ts) does nothing but resolve a CSV row into exactly the same shape those manual paths already produce, then reuses their target tables directly.
18. **Platform hardening**: deployment pipeline, accessibility and security pass across everything built, performance/testing hardening.

Rationale for this order: it front-loads the two things every later feature depends on — tenancy/security (phase 1) and the append-only historical-record pattern (phases 3–5) — so those patterns are established once and reused, rather than retrofitted after multiple modules already violate them.
