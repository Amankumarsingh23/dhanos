# DhanOS — Implementation Status

Last updated: 2026-07-21.

## 0. Baseline

The engineering foundation phase is complete. Framework, tooling, typed env validation, Supabase client plumbing, shared UI components, and app routing scaffolding are in place — see section 1. No financial modules (accounts, transactions, investments, etc.) exist yet; those begin with phase 1 of the recommended order in section 3.

## 3. Recommended implementation order

Sequenced so each phase is independently useful and later phases depend on earlier data existing, rather than building UI for data that can't exist yet:

1. **Foundation**: repo scaffold (Next.js + TypeScript + pnpm) ✅, environment variable setup ✅, base layout shell ✅, household + membership model with RLS (roles, status, idempotent creation) ✅, auth (sign up/in/out, verification, password reset, protected routes, onboarding that creates both the profile and the household, `profiles` table) ✅, authenticated app shell (navigation, mobile nav, privacy mode) ✅ — remaining: a real (hosted) Supabase project for staging/production, and a collaboration-invite flow to actually add a second person to an existing household.
2. **Core ledger**: institutions, accounts, transactions (income/expense/transfer discriminated), recurring commitments. Schema complete (`people`, `institutions`, `financial_accounts`, `account_balance_snapshots`, `transaction_categories`, `transactions`, `transaction_splits`, `recurring_rules`, `attachments`, `activity_events` — see [database-plan.md](./database-plan.md), [financial-domain-model.md](./financial-domain-model.md)). **People, Institutions, Accounts, Categories, and Transactions now have full CRUD UI** (`/app/people`, `/app/institutions` — PROMPT 8; `/app/accounts` — PROMPT 9; `/app/cash-flow` + `/app/cash-flow/categories` — PROMPT 10), built first per this phase's own ordering since loans/policies/investments will all reference them. Recurring commitments (`recurring_rules`) is the one piece of this phase still schema-only — no generation job or UI creates/consumes a recurring rule yet, though `transactions.recurring_rule_id` is ready to receive that link.
3. **Net worth foundation**: assets (movable/immovable), liabilities, valuation snapshots, net-worth snapshot rollup — deliberately before investments/loans, since net worth needs *something* to sum even in a minimal form, and validates the append-only snapshot pattern early.
4. **Investing**: investments, SIPs, staking positions, layered onto the valuation-snapshot mechanism already built.
5. **Debt**: loans (with principal/interest-split payments), lending/receivables — reuses the append-only payment-history pattern from step 4.
6. **Protection & property depth**: insurance policies, richer asset tracking, documents (attachments now have real entities to attach to).
7. **Planning**: goals, emergency-fund planning, monthly financial closing (needs steps 2–6's data to close against).
8. **Insight layer**: reports (with cutoff dating), projections/calculators (with assumption disclosure), reminders, financial decision journal, financial-literacy content.
9. **Platform hardening**: data export, deployment pipeline, accessibility and security pass across everything built, performance/testing hardening.

Rationale for this order: it front-loads the two things every later feature depends on — tenancy/security (phase 1) and the append-only historical-record pattern (phases 3–5) — so those patterns are established once and reused, rather than retrofitted after multiple modules already violate them.
