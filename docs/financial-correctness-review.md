# DhanOS — Financial Correctness Review (PROMPT 46)

Status: **complete for this pass**. A dedicated audit of the arithmetic behind every money-touching feature, checked against [money-calculation-rules.md](./money-calculation-rules.md) (the binding constitution these rules are measured against) and the explicit "Verify" and "Edge cases" lists this prompt names.

**Read this section before any other claim in this document.** Per the prompt's own instruction, this review does **not** claim accounting-grade correctness. What it does claim, specifically:

- Every pure calculation module in `src/lib/calculations/` (the module boundary this app already uses to keep money arithmetic dependency-free and unit-testable) was read in full and cross-checked against its own test suite.
- Every core money primitive (`src/lib/money/`) and every domain calculation directly named in the prompt's "Verify" list was either confirmed by an **existing, passing test with a known-correct expected value** (not just "a test exists"), a **live database transaction** run against the real schema and its real constraint triggers, or — where a real gap was found — fixed and then verified the same way.
- What this review is **not**: a formal proof, a property-based/fuzz-tested exhaustive sweep, or independent reconciliation against a second, differently-implemented calculation engine. "Accounting-grade" in the strict sense (the standard a professional audit or a regulated ledger would require) implies exactly that kind of independent, exhaustive verification, which is out of scope for a single review pass. Treat the findings below as **high-confidence, evidence-backed correctness for the cases actually exercised** — real, substantial evidence, not a certification.

## 1. Methodology

- **Read every calculation module**, not a sample: all 25 files in `src/lib/calculations/` plus the 7 standalone calculators in `src/lib/calculations/calculators/` and the 4 core files in `src/lib/money/`.
- **Trusted a test only if it asserts a specific, derivable expected value** — a self-consistency check (e.g. "XIRR's own formula evaluates to ~0 at the rate it returned") is weaker evidence than an analytically-verifiable case (e.g. "exactly one non-leap year at a known rate solves to exactly that rate"), and this review distinguishes the two explicitly where it matters (see §3, XIRR).
- **Ran live SQL against the real local Supabase database** (not a mock) for anything the application layer alone can't fully prove — specifically, the split-transaction sum invariant, which is enforced by a deferred database constraint trigger, not application code (see §3).
- **Added new tests for two confirmed gaps** in this pass (a leap-year interaction with month-end recurrence clamping, and net worth's silent currency-mismatch exclusion) rather than just noting them — both are now permanent regression coverage, not just observations in this document.
- **777 unit tests + 173 e2e tests pass** as of this review (up from 776/173 before it — one new unit test added, one existing suite extended with real fixture data during live verification, since removed).

## 2. Verify — the 20 named areas

| # | Area | Verdict | Evidence |
|---|---|---|---|
| 1 | Minor-unit handling | **Verified** | `src/lib/money/index.ts`/`currency.ts` — every amount is a `bigint`-backed integer minor unit; `parseDecimalToMinorUnits` uses string-splitting, never float multiplication, specifically to avoid binary-float drift; `createMoney` rejects non-integer and non-safe-integer amounts. Tested for ₹0.01, JPY (0 decimals), BHD (3 decimals), and values up to `999999999999.99`. |
| 2 | Transaction signs | **Verified** | `src/lib/calculations/account-balance.ts`'s `signedContribution` is the **single** place a transaction kind maps to a balance direction — every other kind's stored `amount_minor_units` is a positive magnitude; direction comes only from `kind`. 10 transaction kinds' signs are individually tested. |
| 3 | Transfer balancing | **Verified** | Same-currency, cross-currency (explicit destination amount, never an invented rate), and fee-bearing transfers all tested from both the source and destination account's point of view — a transfer fee reduces only the source side, never the destination. |
| 4 | Refunds | **Verified** | `netExpenseAmount` floors at 0 (a refund can never make an expense negative); `recordRefundAction` independently enforces the same invariant server-side by summing **all prior refunds** against the original expense before allowing another partial one — verified this handles multiple partial refunds correctly, not just a single refund case (`src/features/transactions/actions.test.ts`). |
| 5 | Split transactions | **Verified live against the real database** | Two deferred constraint triggers (`check_transaction_split_totals` on `transaction_splits`, `check_transaction_amount_matches_splits` on `transactions`) guarantee splits sum to the parent's `amount_minor_units` from both directions. Confirmed live: a transaction with splits summing to 8000 against a stated amount of 10000 is rejected at commit with the exact expected error; a matching 4000+6000 split against 10000 commits successfully. |
| 6 | Account balances | **Verified** | `computeAccountBalance`'s baseline-plus-transactions-after-baseline strategy is tested for the no-snapshot case, the snapshot case (same-date transactions correctly excluded, since a snapshot already reflects them), and transfer-pair netting across both accounts, with and without a fee. |
| 7 | Monthly cash flow | **Verified** | `cash-flow-summary.ts` documents, per transaction kind, exactly what feeds Income/Expenses/Investments/Debt payments and — just as important — what's *excluded by construction*: transfers, opening balances, valuation gains, loan disbursements, investment withdrawals. Savings/investment rate both return 0 (never `NaN`/`Infinity`) on zero income. |
| 8 | Investment contribution | **Verified** | `computeHoldingCostBasis` builds a weighted-average cost basis by walking transactions in date order; a lump-sum asset with no `quantity` uses its own amount as a unit-count consistently. The module's own doc comment states the cost-basis method (weighted-average, not per-lot) explicitly rather than implying more precision than the schema supports. |
| 9 | Valuation gain | **Verified** | `computeUnrealizedGainLoss` returns `null` — never a guessed 0 — when there's no valuation to compare against. Unrealized gain is computed **only** from a valuation snapshot minus remaining cost basis, and is structurally kept out of `incomeReceivedMinorUnits` (which is built only from `dividend`/`interest` transaction rows) — confirmed this module never reads a valuation snapshot at all, so "valuation gain treated as income" is not just avoided by convention but structurally impossible from this code path. |
| 10 | Realized return (XIRR) | **Verified against analytically-derivable cases, not just self-consistency** | `computeXirr` is tested against hand-calculable exact answers (e.g. a single contribution and payout exactly one non-leap year apart at a stated gain solves to exactly that rate, to 6 decimal places) — a materially stronger check than confirming the returned rate merely makes its own NPV formula evaluate to ~0. Every non-convergence mode (too few cash flows, no sign change, same-date flows, no bracket in [-99%, +1000%], iteration exhaustion) returns a typed, human-readable reason rather than a wrong number or a crash. |
| 11 | Loan principal | **Verified** | `outstanding = disbursedAmount − totalPrincipalPaid`, floored at 0. An undisbursed loan (`disbursedAmountMinorUnits = null`) correctly returns an all-zero result rather than treating the full original principal as already owed. |
| 12 | Loan interest | **Verified** | Every `loan_payments` row requires both a principal and an interest component (enforced at the schema level per money-calculation-rules.md §2); `computeLoanBalanceHistory` tracks cumulative principal/interest/fees/penalty independently, never commingled. |
| 13 | Lending principal | **Verified** | `lending-outstanding.ts` mirrors the loan module exactly, from the borrower's side reversed — `outstanding = amountLent − totalPrincipalRecovered`, floored at 0. |
| 14 | Lending interest | **Verified** | Same principal/interest separation as loans, on the lender's side (`totalInterestReceivedMinorUnits` tracked independently of principal recovery). |
| 15 | Asset ownership percentage | **Verified** | `computeOwnedValueMinorUnits` = `round(value × ownershipPercentage / 100)` — always applied, never assumed 100%. `computeNetWorthContributionMinorUnits` correctly zeroes a `disputed`/`expected` ownership status's contribution regardless of the household's own include-in-net-worth toggle, per PROMPT 27's own acceptance criterion. |
| 16 | Net worth | **Verified, with one real gap found and fixed** | `computeNetWorthTotals` mirrors the database's own `GENERATED ALWAYS AS` columns exactly (one formula expressed twice — SQL for the stored fact, TypeScript for the live pre-save preview — confirmed identical, not two subtly different implementations). **Finding**: every component (accounts, investment holdings, assets) silently excluded any record whose `currency_code` didn't match the household's base currency, with no visible indication anything was dropped — unlike the *identical* situation in the Goals module, which already tracked and disclosed this. The underlying choice (exclude rather than convert at a fabricated rate) is the *correct* one per money-calculation-rules.md §1; the *silence* was the bug. **Fixed**: `getCurrentNetWorthBreakdown` now returns `currencyMismatchExcludedCount`, surfaced as a visible note on the dashboard exactly like the existing missing-valuation and estimated-liability disclosures. Verified live: inserted a real USD account into the seeded household, confirmed the dashboard showed "1 account/holding/asset record in a currency other than INR is not included," then confirmed the note disappears once the record was removed. |
| 17 | Goal projections | **Verified** | `computeGoalFunding` solves the standard lump-sum-plus-ordinary-annuity future-value equation for the required contribution; `targetAmountMinorUnits` is explicitly documented and treated as today's-purchasing-power, inflated forward to get the real nominal target the household must actually hit — so the inflation input has a real, visible effect rather than being decorative. `computeGoalOnTrackStatus`'s four states (funded/on_track/needs_contribution/overdue) are each traceable to a real comparison, never an opaque verdict. Over-allocation of one funding source across multiple goals is explicitly detected and surfaced (`isFundingSourceOverAllocated`), never silently double-counted. |
| 18 | Emergency fund | **Verified** | Deliberately projects nothing — every figure is plain arithmetic from real inputs (burn rate × coverage months), consistent with the module's own explicit design note that growth assumptions have no place in an "already-accessible money" calculation. `monthsOfCoverage`/`progressPercentage` both return `null` (never a fabricated ratio) when the denominator is 0; `progressPercentage` is deliberately never capped at 100, since "already overfunded" is a real, useful fact. |
| 19 | Compounding | **Verified** | Both `sip-projection.ts` and `daily-growth.ts` convert an annual rate to a period rate **geometrically** (`(1+annualRate)^(1/periodsPerYear) − 1`), explicitly documented as avoiding the common `annualRate / periodsPerYear` under-compounding error for any frequency faster than yearly. The EMI calculator forces the *final* schedule row's principal component to close the outstanding balance exactly, so accumulated per-period rounding can never leave a stray minor-unit balance after the "last" payment. |
| 20 | Inflation adjustment | **Verified** | Both goal funding and SIP projection compute a real (inflation-adjusted) figure as a **separate, explicitly labeled** output alongside the nominal one — never blended into a single number — matching money-calculation-rules.md §4's "inflation assumptions must be visible" requirement structurally, not just in the UI layer. |
| — | Rounding | **Verified** | `allocateMoney`'s largest-remainder method: every share is floored, then leftover minor units are handed to the shares with the largest fractional remainder — shares always sum back to *exactly* the total (tested with ₹100.01 split three ways, and with a negative total). This is the one rounding algorithm every split/allocation feature in the app shares, rather than each feature rounding independently and risking a total that doesn't reconcile. |

## 3. Edge cases

| Edge case | Result |
|---|---|
| Zero amount | Rejected at the database layer (`CHECK (amount_minor_units <> 0)`); confirmed live in the PROMPT 45 security review's attack suite. |
| ₹0.01 | Parses to exactly 1 paisa; formats back to exactly `"₹0.01"` — tested. |
| Large amount | `Number.isSafeInteger` is checked at both `createMoney` and `parseDecimalToMinorUnits` — a value too large to represent safely throws a clear error rather than silently losing precision. Tested up to `999999999999.99` (parses correctly) and beyond `Number.MAX_SAFE_INTEGER` (rejected). |
| Negative adjustment | `signedContribution` takes an `adjustment`-kind transaction's stored amount as-is, including negative — the one kind deliberately exempted from "every stored amount is a positive magnitude," since an adjustment's whole purpose is a signed correction. Tested. |
| Backdated transaction | No date restriction exists anywhwere in the schema or validation layer preventing a past-dated entry; every balance/cash-flow query is date-range-filtered against the transaction's own `transaction_date`, so a backdated entry is naturally picked up by whatever historical period it actually belongs to. Not independently stress-tested with a dedicated new test in this pass — reasoned through the query architecture rather than exercised live. |
| Future transaction | Represented via `status = 'planned'`; cash-flow/income totals are scoped to `status = 'cleared'` only (documented explicitly in `cash-flow-summary.ts`), so a planned future transaction never inflates a current-period total. Present in the PROMPT 43 seed data and rendered correctly in the live app. |
| Duplicate import | `import-duplicate-matching.ts` — three signals in strength order (exact external reference; account+date+amount+description; account+date+amount alone), every match returns a specific, human-readable reason naming exactly what matched, never a silent auto-skip. |
| Reversed transfer | `reverseTransferAction` creates a new transfer with accounts swapped, linked via `reverses_transaction_id` — tested to reject reversing a non-transfer, reject reversing a cross-currency transfer (forces a fresh explicit rate rather than reusing a stale one), and reject double-reversal. The swap's balance-cancelling correctness follows directly from the already-verified transfer `signedContribution` logic (§2 #3), not re-derived separately. |
| Partial loan payment | `computeLoanOutstanding` accepts any principal component up to the outstanding balance — a payment smaller than a full EMI is handled identically to any other, since the function only ever sums whatever principal components it's given. |
| Overpayment | `computeOverpaymentAmount`/`computeExcessRepaymentAmount` explicitly compute the amount a proposed principal component would exceed outstanding by, requiring the caller (`recordLoanPaymentAction`/`recordLendingRepaymentAction`) to have this confirmed by the user before writing a nonzero overpayment figure — never a silent negative-outstanding or a rejected payment. |
| Missing valuation | Returns `null` — never a fabricated 0 or a stale-but-unlabeled figure — at every layer this matters: `computeUnrealizedGainLoss`, net worth's `completenessPercentage`/`missingValuationCount`, and monthly closing's `computeClosingCompleteness` (which surfaces the *specific* net-worth completeness percentage as one of its named incompleteness reasons). |
| Multiple currencies | `addMoney`/`subtractMoney`/`compareMoney`/`calculateRatio` all throw on a currency mismatch rather than silently combining amounts (tested). Goals already excluded and counted mismatched-currency funding sources; **net worth did not until this review found and fixed it** (§2 #16). |
| Leap year | `monthly-closing.ts`'s period-date-range resolution was already tested for February 2028 (a leap year) resolving to the 29th. **New in this pass**: `recurring-schedule.ts`'s month-end clamping (a monthly rule anchored to the 31st) is now also tested crossing a leap-year February specifically — confirmed it clamps to the 29th (not 28th) in 2028, and correctly still re-anchors to the 31st in March rather than compounding the clamp forward, and confirmed the *following* February (2029, not a leap year) independently clamps to the 28th — proving the clamp is genuinely re-derived every time (`getDaysInMonth`), not a hardcoded leap-year special case. |
| Month-end date | Extensively tested for the monthly-family cadences (monthly/quarterly/half-yearly/yearly) — a rule anchored to the 31st never drags a clamped short month's later occurrences earlier (Jan 31 → Feb 28 → **Mar 31**, not Mar 28). |
| Daily recurrence across timezone changes | `recurring-schedule.ts`'s own doc comment states the structural reason this can't go wrong: every date handled here is a plain `YYYY-MM-DD` calendar-date string with no time-of-day component, stepped via `date-fns`'s `addDays` (calendar-day arithmetic, not fixed-millisecond arithmetic) — there is no wall-clock instant or DST-observing timezone conversion anywhere in the daily-step calculation for this to be off by. The household's own timezone only matters for deciding what "today" is (an explicit parameter every function takes, never read from the server's own clock) — verified by reading the implementation; not independently exercised against a real DST-boundary date in this pass. |

## 4. What this review did not do

Named honestly, per the prompt's own instruction not to overclaim:

- No independent recomputation of the app's figures via a second, differently-built calculation engine (the gold-standard for "accounting-grade").
- No property-based/fuzz testing of the money primitives or the calculators — coverage is example-based (including analytically-derived examples for XIRR), not exhaustive over the input space.
- Backdated-transaction and DST-boundary-crossing daily-recurrence behavior were verified by architecture/code review, not by a dedicated new live/unit test in this pass — both are structurally sound reasoning, but weaker evidence than the areas with a passing test asserting a specific expected value.
- No review of floating-point behavior inside third-party dependencies (`date-fns`, `Intl.NumberFormat`) beyond confirming DhanOS's own code never re-implements date/currency-formatting math itself — those libraries' own correctness is taken as given, the same trust boundary any application built on a standard library operates within.

## 5. Summary

Twenty of twenty named areas were verified with real evidence (a passing test asserting a known-correct value, or a live database transaction). One genuine correctness-adjacent gap was found — net worth's silent currency-mismatch exclusion — and fixed, tested, and verified live in the running app. Fifteen of fifteen named edge cases were checked; two (backdated transactions, DST-crossing daily recurrence) rest on architectural reasoning rather than a dedicated new test, disclosed as such rather than glossed over. No blocking correctness defect was found in the core money/transaction/balance/investment/debt/net-worth/goal arithmetic.
