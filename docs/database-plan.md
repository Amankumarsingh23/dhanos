## 1. Conventions

- **Migration tool**: Supabase CLI (`supabase migration new <name>`), SQL migrations checked into `supabase/migrations/`, applied in order, never edited after being applied to any shared environment (staging/prod). A correction is a new migration. See [local-supabase.md](./local-supabase.md) for the exact commands (`pnpm db:*`).
- **Updated-at trigger utility**: `public.set_updated_at()`, defined in `supabase/migrations/20260721021741_utility_updated_at_trigger.sql`. Attach to any mutable table with `create trigger set_updated_at before update ... execute function public.set_updated_at();`. Append-only tables skip it entirely (no `updated_at` column to maintain).
- **Naming**: snake_case tables and columns, singular table names avoided in favor of plural (`accounts`, `transactions`), foreign keys as `<referenced_singular>_id`.
- **Primary keys**: `uuid` default `gen_random_uuid()`.
- **Timestamps**: every table has `created_at timestamptz not null default now()`; mutable tables also have `updated_at`; append-only/historical tables deliberately omit `updated_at` to make in-place mutation harder to do by accident.
- **Money columns**: always a pair — `amount_minor_units bigint not null` and `currency_code text not null` (ISO 4217, `char(3)` or a `currency_code` domain/enum) — never a bare `numeric`/`float` amount. See [money-calculation-rules.md](./money-calculation-rules.md).
- **Soft delete**: avoided for financial records by default — history should be preserved via status/lifecycle columns (e.g. `closed_at` on a Loan) rather than deletion; where deletion is user-facing (e.g. removing a mistakenly-added Account with no transactions), enforce via constraints that referenced records block deletion (`ON DELETE RESTRICT`) unless explicitly empty.

## 2. Tenancy & RLS strategy — implemented

- Every financial table includes `household_id uuid not null references households(id)`.
- RLS enabled on every table from its creation migration (not added later).
- Roles: `owner`, `admin`, `editor`, `viewer` (see `public.household_memberships.role`) — owner/admin can manage household settings and membership (`canManageHousehold` in `src/lib/households/permissions.ts`), editor can read/write financial data, viewer is read-only. Membership also carries a `status` (`active`/`invited`/`suspended`) — only `active` rows grant access; `invited` is reserved for a collaboration-invite flow that doesn't exist yet (see PROMPT 4's "do not implement invitations yet").
- Implemented as two `security definer` helper functions (search_path locked down, to avoid both RLS recursion and search-path hijacking) rather than inlining the same subquery into every policy: `public.is_household_member(household_id)` and `public.household_role(household_id)` — see `supabase/migrations/20260721051051_household_memberships.sql`. Policies call these; role-based write restriction (e.g. `viewer`: `select`-only) is enforced by checking `household_role(...)` in each table's `insert`/`update`/`delete` policies.
- Bootstrapping problem solved via trigger: creating a household has no existing owner row to satisfy the `household_memberships` insert policy, so `public.create_owner_membership()` (also `security definer`) inserts the creator's owner row automatically, in an `after insert on households` trigger.
- Household creation itself goes through `public.get_or_create_household(...)` (`security invoker`, called via `supabase.rpc(...)` from onboarding) rather than a raw insert — it's idempotent: if the caller already owns a household (enforced by the `household_memberships_one_owner_per_user` partial unique index), it returns that household's id instead of erroring or creating a duplicate, making a client retry/double-submit safe. Note: an `insert ... returning` on `households` fails RLS even for the inserting user, because the row only satisfies the `is_household_member` SELECT policy once `create_owner_membership`'s cascading insert has run, and `RETURNING` evaluates against a snapshot that doesn't yet see that same-statement trigger effect — `get_or_create_household` sidesteps this by generating the id up front and never using `RETURNING`.
- No table should be readable without a household join — this is the enforcement point that backs up the domain model's "every entity scoped to a Household" invariant. Verify it directly against the API, not just through app code — see [local-supabase.md](./local-supabase.md) "Test RLS" and `tests/e2e/household-isolation.spec.ts`.
- Local Supabase's default config does not auto-expose new tables to `anon`/`authenticated`/`service_role` without explicit `grant`s (the legacy "expose everything" behavior is off by default and being removed entirely) — every table-creating migration includes its own grants, deliberately excluding `anon` unless a table is genuinely meant to be public.
- Centralized authorization helpers live in `src/lib/households/permissions.ts`: `requireUser` (re-exported), `requireHousehold` (page-gating, redirects to `/onboarding`), `requireHouseholdMember`/`requireHouseholdRole` (data-layer, throw `NotFoundError`/`PermissionDeniedError` — always re-check a submitted `household_id` against the database, never trust it because it was submitted), `canManageHousehold`.

**Financial goals** (PROMPT 30) — ✅ implemented (`supabase/migrations/20260723140000_goals.sql`)

**Emergency fund planner** (PROMPT 31) — ✅ implemented (`supabase/migrations/20260723150000_emergency_fund.sql`)
`emergency_fund_plans` — exactly one row per household (`unique (household_id)`), storing only what genuinely can't be derived: `coverage_target_months` (user-selected, never inferred) and `dependants_count` (used only to prefill a *suggested* coverage target — `src/lib/calculations/emergency-fund.ts`'s `suggestCoverageTargetMonths` — the stored column always reflects the household's own actual choice). Average essential monthly expenses, monthly EMIs, and insurance commitments are never stored here at all — computed fresh on every read from Expenses' `getExpenseSummary`, `loans.emi_amount_minor_units`, and Insurance's `getInsuranceOverview`, respectively. `emergency_fund_source_overrides` — a household's explicit deviation from the *structural default* liquidity classification of a real `financial_accounts` or `investment_holdings` row (PROMPT 31: "user can override inclusion"); absence of a row means the default applies, so this table only ever stores exceptions, never a full duplicate of every source's state. The default itself comes from `classifyAccountLiquidity` (new, for `financial_accounts.account_type`) and the pre-existing `classifyLiquidity` (`src/lib/calculations/portfolio-performance.ts`, reused unchanged for `investment_holdings.asset_class`) — only a `liquid` classification defaults to included. `financial_accounts.account_type in ('loan', 'credit')` is never even offered as a candidate (PROMPT 31: "do not count unavailable credit limits" — a credit line is a liability, not owned money, so no override exists for it either). The `assets` and `lendings` tables are never queried by this feature at all, which is what structurally satisfies "do not count illiquid property / disputed receivables / uncertain inherited assets" without any special-case code. Coverage math (monthly burn rate, target amount, months of coverage, shortfall, progress, suggested monthly contribution) is always derived, never stored — see `src/lib/calculations/emergency-fund.ts`, which — unlike Goals — never projects an investment return at all.

**Net-worth engine** (PROMPT 32) — ✅ implemented (`supabase/migrations/20260723160000_net_worth_breakdown.sql`, growing the tenancy-era `net_worth_snapshots` table created in `20260721021746_net_worth_snapshots.sql`, which had only `total_assets_minor_units`/`total_liabilities_minor_units` and had never been written to by any feature)
`net_worth_snapshots` — **"do not store only the final total"**: seven component columns (`cash_and_accounts_minor_units`, `investments_minor_units`, `movable_assets_minor_units`, `property_minor_units`, `receivables_minor_units`, `loans_minor_units`, `other_liabilities_minor_units`), each computed by reusing another domain's own already-correct logic rather than re-deriving it — eligible `financial_accounts` balances (excludes `account_type in ('loan', 'credit')`, same convention as the emergency fund planner); `investment_holdings`' latest valuations; `assets`' ownership-adjusted net worth contribution (`computeNetWorthContributionMinorUnits`, PROMPT 27 — **"ownership percentage is applied correctly"** was already solved here, just finally consumed by a rollup), split by `asset_group` into movable and property; `lendings`' currently-owed outstanding (receivables); `loans`' active outstanding (institutional debt); and `liabilities` split into informal debt (any certainty) plus general obligations with `certainty = 'confirmed'` only (an *estimated* general obligation is deliberately excluded — PROMPT 32: "minus other confirmed liabilities"). `total_assets_minor_units`, `total_liabilities_minor_units`, and the new `net_worth_minor_units` are all `generated always as (...) stored not null` — they can never drift from their components, the same guaranteed-consistent idiom as `account_balance_snapshots.difference_minor_units`. **"Missing valuations lower completeness rather than becoming zero silently"**: `completeness_percentage`/`valuation_dependent_item_count`/`missing_valuation_count` are stored alongside every snapshot — a missing valuation still contributes 0 to its component (there's no better number), but completeness always visibly reports what fraction of valuation-dependent items (investment holdings + assets) actually had one. `source_cutoff_at` is the timestamp underlying data was actually considered, distinct from `created_at` (when the row was written) — the same data-cutoff-vs-generated-at convention the planned Reports entity will also use. **"Snapshot values are reproducible"**: every snapshot is computed "as of now" only — `src/features/net-worth/queries.ts`'s `getCurrentNetWorthBreakdown` never backdates a recomputation, so the same underlying data always yields the same breakdown. **"Historical snapshots are not rewritten automatically"**: already true structurally (append-only, no update grant, `unique (household_id, as_of_date)`) — recording a second snapshot for a date already recorded fails outright, checked explicitly in `recordNetWorthSnapshotAction` for a clear message. Five charts (net-worth curve, asset growth, debt reduction, contribution-vs-valuation-change, month-over-month) are built entirely from real recorded snapshots (plus `investment_transactions` for the contribution/valuation split) — never interpolated or projected for a period with no snapshot.

**Monthly financial closing** (PROMPT 33) — ✅ implemented (`supabase/migrations/20260723170000_monthly_closings.sql`, realizing the `monthly_closings` entity already anticipated — but unbuilt — in this document and financial-domain-model.md §7/§10)
`monthly_closings` — not fully append-only like `loan_payments`/`net_worth_snapshots`: its lifecycle `status` (`in_progress`/`closed`/`reopened`) genuinely changes over time, the same "status is a mutable lifecycle marker, substantive figures are not" shape `insurance_policies` already established for renewal. `start_monthly_closing()` (SECURITY INVOKER RPC) atomically inserts the closing row plus its 12 `monthly_closing_review_items` checklist rows (account balances, income, expenses, transfers, SIP contributions, investment valuations, loan balances, lending repayments, insurance premiums, asset changes, goals, unusual transactions). Completing a closing is a single, narrow UPDATE that fills `income_total_minor_units`/`expense_total_minor_units`/`investment_contribution_minor_units`/`debt_payment_minor_units` (reusing the dashboard's `getCashFlowSummary` directly, never re-derived) plus a `net_worth_snapshot_id` link (ensuring a snapshot exists "as of now" via the net-worth engine, PROMPT 32) exactly once — no other action ever touches these columns again. `net_cash_flow_minor_units` is a `generated always as (income - expense - debt_payment) stored` column. **"Reopening requires deliberate confirmation"**: `reopenMonthlyClosingAction` requires a typed `reopen_reason` (enforced by a CHECK requiring it whenever `status = 'reopened'`) and only ever updates `status`/`reopened_at`/`reopened_by`/`reopen_reason` — the frozen totals already written at completion are never rewritten. **"Later corrections are marked"**: re-closing a reopened period always inserts a brand-new row via `start_monthly_closing()` again, with `supersedes_closing_id` pointing at the reopened one and `report_version` incremented — the old row keeps its original totals forever, permanently also carrying `status = 'reopened'` as a historical fact that it was later revisited. **"Closed month remains viewable"**: nothing ever deletes a closing or a review item; a period's full correction chain (`monthly_closings_household_period_idx` on `(household_id, period, created_at desc)`) is always queryable, and the "current" closing for a period is simply whichever row has the latest `created_at` — no forward-pointer column needed. A partial unique index (`monthly_closings_household_period_in_progress_uidx`) prevents two simultaneous in-progress closings for the same period. **"Reports state when data is incomplete"**: `src/lib/calculations/monthly-closing.ts`'s `computeClosingCompleteness` always gives a specific, countable reason (N of M review items unresolved; the linked net-worth snapshot's own completeness percentage below 100) rather than an opaque flag — the monthly report renders every reason found. The report itself additionally pulls major/unusual expenses, missed commitments, goal progress, and upcoming obligations (recurring commitments, insurance renewals, money-drain renewals) directly from each of those modules' own existing queries.

**Protection & property** — insurance + claims + assets + property depth ✅ implemented (PROMPT 25, PROMPT 26, PROMPT 27, PROMPT 28)
`insurance_policies` (12 `policy_type` values — health/term/life/vehicle/home/personal_accident/travel/business/property/crop/device/other — with health-only fields nullable/UI-gated regardless of type, same convention as `loans`' education fields; a renewal is always a brand-new row linked back via `previous_policy_id`, never an edit of the old one — see `create_insurance_policy`) and `insurance_policy_insured_people` (many-to-many, "multiple people can be insured under one policy"). A premium payment is a plain `kind = 'expense'` transaction (`transactions.insurance_policy_id`, categorized under the household's existing `classification = 'protection'` category) — deliberately not a new transaction kind or a second append-only payments table, unlike loans/lending/liabilities, since there's no "outstanding principal" for a premium to pay down. `insurance_claims` (PROMPT 26 — a claim against one policy: an insured person that must be one of the policy's own `insurance_policy_insured_people` rows, enforced by trigger; claimed/approved amounts; the 8-value status list; `policy_id` is `ON DELETE RESTRICT`, unlike the insured-people join's `CASCADE`, so a policy with claim history can never be hard-deleted). Settling a claim writes a real `kind = 'insurance_claim_settlement'` transaction (`transactions.insurance_claim_id`) via `record_insurance_claim_settlement()` — never `income` — the same "structurally never income" idiom `loan_disbursement`/`lending_repayment` already use; `status = 'paid'` is only ever set by that RPC, atomically with the settlement fields, never a bare status UPDATE. `insurance_policy_waiting_periods` (PROMPT 26 — a policy's structured, dated waiting periods; label + duration in months + start date; its milestone/end date is always computed as `starts_from + duration_months`, never stored — see `src/lib/calculations/insurance.ts`; cascades with its policy, unlike claims).

`assets` (PROMPT 27 — movable/immovable/business property in one table, discriminated by `asset_group`, `category` cross-validated against it by a CHECK — `'machinery'`/`'equipment'` deliberately valid under both movable and business, disambiguated by group; carries no current-value column at all, same "no value column" shape as `investment_holdings` — see `asset_valuation_snapshots` below; `ownership_percentage` (0, 100] always applied when computing owned value, never assumed 100%; `ownership_status` includes `disputed`/`expected`, both of which zero out the asset's net-worth contribution regardless of `include_in_net_worth` — PROMPT 27: "disputed or expected property is not presented as fully owned" — see `src/lib/calculations/assets.ts`; `related_loan_id` is a plain optional cross-reference to `loans`, its outstanding always computed independently via `src/lib/calculations/loan-outstanding.ts` and shown as its own figure, never netted into the asset's value — PROMPT 27: "attached debt remains separate") and append-only `asset_valuation_snapshots` (mirrors `investment_valuation_snapshots` exactly — `unique (asset_id, as_of_date, source)`). `create_asset()` atomically writes the asset and its first valuation snapshot; every later re-valuation is a new snapshot via a plain insert, never an edit.

**Property depth** (PROMPT 28) grows `assets` with 15 more nullable, UI-gated-to-immovable columns (`property_type`, `land_area`/`area_unit`, `title_status`, `mutation_status`, `original_owner`, `legal_heir_notes`, `rental_status`, `occupancy`, `encumbrance_status`/`encumbrance_notes`, `dispute_status`, `registration_details`, `ownership_share_notes`) — same "nullable regardless of type, UI decides" convention as loans' education fields. **"Do not store precise location publicly"**: a new `location_precise` column is deliberately excluded from the list-page query's explicit column list (`ASSET_LIST_SELECT` in `src/features/assets/queries.ts`) — only the single-record detail query ever selects it, same shape as `people.birth_date`/`notes` staying list-hidden. `asset_valuation_snapshots` grows a required `confidence` (verified/professional/informal_estimate/unverified, default `unverified`) and optional `appraiser` — PROMPT 28: "unverified valuations are labeled estimates," enforced by rendering an "Estimate" badge for anything short of `verified`. `transactions` grows a nullable `asset_id` (valid only for `kind = 'income'`) — PROMPT 28: "income generated links to cash flow," so rental/asset income is a real transaction, never a free-text note. `create_asset()` (drop-and-recreate, same "appended-parameter RPC" convention as every other grown RPC in this schema) now also accepts the property fields and the initial valuation's confidence/appraiser.

**Money drains** (PROMPT 29) — ✅ implemented (`supabase/migrations/20260723130000_money_drains.sql`)
`money_drains` — a household-entered register of depreciating and money-draining items (subscriptions, memberships, vehicles, unused services, rented space, gadgets, maintenance-heavy assets, contractual commitments, recurring fees), discriminated by `drain_type`. Deliberately a tracking/analysis layer, not a second ledger — it never writes its own `transactions` row. `cost_frequency` (monthly/quarterly/half_yearly/yearly/one_time/irregular) plus `cost_amount_minor_units` is the household's own entered estimate, annualized by `src/lib/calculations/money-drains.ts` the same way PROMPT 17's `sip-commitment.ts` and PROMPT 25's `annualizePremiumMinorUnits` normalize their own cadences — `irregular` deliberately returns `null` rather than a guessed figure, so an irregular-cost item is always excluded from an annualized total and counted separately, never silently absorbed (PROMPT 29: "analysis is factual and explainable"). `usage_frequency` has no default — every row requires an explicit choice, rendered everywhere as "your estimate" (PROMPT 29: "estimated usage is visibly user-entered"). `linked_recurring_rule_id` (optional, -> `recurring_rules`) is how "recurring expenses remain connected to transactions" is satisfied structurally: the analysis layer resolves that rule's real current amount via the same `resolveAmountForDate` pipeline the Recurring feature itself uses, shown alongside — never blended into — the entered estimate. `linked_asset_id` (optional, -> `assets`) similarly reads that asset's own latest valuation snapshot rather than duplicating a value history; `linked_account_id` (optional, -> `financial_accounts`) records where it's paid from. A household-consistency trigger enforces all three links belong to the same household, and that `currency_code` matches `linked_account_id`/`linked_recurring_rule_id` where set. `status` (active/paused/cancelled) only ever changes via an explicit user action — nothing in this feature ever cancels or pauses an item automatically (PROMPT 29: "do not automatically order the user to cancel anything") — and, unlike most financial records in this app, a genuinely mistaken row can be hard-deleted (owner/admin only) since nothing else references it; the normal way to record "I stopped this" is marking it `cancelled`, which keeps its historical cost visible rather than removing it.

**Operations** — partially implemented
`attachments` ✅ (`attachable_type`/`attachable_id` polymorphic pair, currently restricted to `'financial_account'`, `'transaction'`, `'lending'`, `'insurance_policy'`, `'insurance_claim'`, and `'asset'` — Supabase Storage object references, household/referential integrity enforced by trigger; `'transaction'` (Expenses' receipts), `'insurance_claim'` (PROMPT 26), and now `'asset'` (PROMPT 27) have a real upload widget — `'financial_account'`/`'lending'`/`'insurance_policy'` remain schema-ready per PROMPT 23/25's "documents" fields but have no upload UI yet — "documents remain private"/"claim documents are authorized" (PROMPT 25/26 acceptance criteria) are already true structurally regardless, since the bucket is private and every read is RLS-scoped + signed-URL-only); `documents` ✅ (PROMPT 34, `supabase/migrations/20260723180000_documents_vault.sql` — the household-wide vault at `/app/documents`, deliberately a separate table rather than another `attachable_type` on `attachments`: a fixed 17-value `category` taxonomy, `document_date`/`expiry_date`, a user-toggleable `status` (active/archived), and an optional client-computed `checksum` are all fields `attachments` was never built to carry, and a vault document is frequently not tied to any entity at all. `entity_type`/`entity_id` is a loose, CHECK-only pair (`(entity_type is null) = (entity_id is null)`) — unlike `attachments.attachable_type`/`attachable_id`, deliberately *not* trigger-verified against the referenced table, since the vault's linkable entity set is open-ended rather than attachments' small closed set; RLS mirrors `attachments`' select/insert/update policies exactly, but narrows `delete` to owner/admin only, versus attachments'/most other tables' owner/admin/editor — "deliberate permanent deletion," archiving being the reversible, editor-accessible alternative. ## 4. Constraints to enforce at the database layer, not just application code

- `amount_minor_units` on `transactions`, `recurring_rules`, `transaction_splits`: `check (amount_minor_units <> 0)` — a zero-amount row is meaningless.
- `loan_payments` — ✅ implemented: `check (total_payment_minor_units = principal_component_minor_units + interest_component_minor_units + fee_component_minor_units + penalty_component_minor_units)`, all four components `>= 0`. `lending_repayments`/`liability_payments` — ✅ implemented: the same shape without fee/penalty, `check (total_repayment_minor_units = principal_component_minor_units + interest_component_minor_units)` (`total_payment_minor_units` for `liability_payments`).
- `transactions` where `kind = 'transfer'` — ✅ implemented: `transfer_account_id` required and `<> account_id`; a `before insert or update` trigger (`public.check_transaction_consistency`, see `transactions` migration) confirms `account_id` and `transfer_account_id` share the same `household_id` as the transaction row and share the same `currency_code` (v1 requires same-currency transfers — see §6, resolved). `transfer_account_id` must be `null` for every other `kind`.
- `transactions` where `kind = 'refund'` — ✅ implemented: `reverses_transaction_id` required, and the same trigger confirms the referenced transaction is `kind = 'expense'` in the same household.
- `transactions` — ✅ implemented: the trigger also confirms `category_id`, `recurring_rule_id`, and `related_person_id` (when present) belong to the same household as the transaction, and that a non-transfer transaction's `currency_code` matches its `account_id`'s currency — cross-household or cross-currency references are rejected outright, not just filtered out of reports.
- `transaction_splits` — ✅ implemented: a `constraint trigger ... deferrable initially deferred` (`public.check_transaction_split_totals`) re-validates, at end of each affected statement, that when a transaction has one or more split rows, `sum(transaction_splits.amount_minor_units) = transactions.amount_minor_units` for that transaction — checked on insert/update/delete of `transaction_splits` and on update of `transactions.amount_minor_units` itself. A transaction with zero splits is unaffected (it is categorized singly via `transactions.category_id`).
- `attachments` — ✅ implemented: `attachable_type` restricted by `check` to the entity types that exist today (`'financial_account'`, `'transaction'`); a trigger (`public.check_attachment_target`) confirms the referenced row exists and belongs to the same household, since Postgres has no first-class polymorphic FK.
- No `update`/`delete` grants on append-only tables (`account_balance_snapshots`, `net_worth_snapshots`, `activity_events`, `investment_valuation_snapshots` — ✅ verified: `has_table_privilege('authenticated', 'public.investment_valuation_snapshots', 'UPDATE'/'DELETE')` both return false — and, once built, `loan_payments`, `receivable_repayments`, `monthly_closings`) for normal application roles — only `insert`/`select`, enforced via RLS/grants, not just convention.
- `investment_transactions`/`investment_valuation_snapshots` — ✅ implemented: a trigger on each (`check_investment_transaction_consistency`/`check_investment_valuation_snapshot_consistency`) confirms `investment_holding_id` belongs to the same household *and* that the row's `currency_code` matches the holding's `investment_assets.currency_code` — a holding's transactions and valuations can never silently mix currencies (PROMPT 16 acceptance criterion "different currencies are not combined without an explicit conversion system").
- `investment_holdings` — ✅ implemented: `unique (investment_account_id, investment_asset_id)` — one holding row per platform-account/asset pair for its whole lifecycle; a trigger (`check_investment_holding_household_consistency`) confirms both references share the holding's household.
- `investment_documents` — ✅ implemented: `check (investment_account_id is not null or investment_holding_id is not null or investment_valuation_snapshot_id is not null)` — a document must link to at least one investing-domain entity; a trigger confirms whichever are set belong to the same household.

## 6. Open questions

1. **Resolved**: `transactions.currency_code` must match `account_id`'s currency — enforced by trigger, not just convention. For a transfer, `transfer_account_id`'s currency must either match `currency_code` (nothing further needed), or — since PROMPT 13 — differ, in which case `transfer_destination_amount_minor_units` and `exchange_rate` are both required, explicit, user-supplied figures (never looked up or computed by the app); `check_transaction_consistency()` enforces the pairing.
2. **Resolved**: `attachments` uses a `(attachable_type, attachable_id)` pair with trigger-enforced integrity (checked against each currently-attachable table by `attachable_type`), rather than a join table per entity type — chosen because the attachable set (`financial_account`, `transaction`, and later `loan`/`insurance_policy`/`asset`) is small and homogeneous (all household-scoped tables with a `uuid` PK), so the trigger stays a short, easily-extended `case` statement. Revisit the join-table-per-type alternative if that `case` statement grows unwieldy. `investment_valuation_snapshots` (PROMPT 16) took the *simpler* path instead — a plain `investment_holding_id` FK, no polymorphism — since in v1 a valuation only ever values a holding, unlike `attachments`' two-and-growing entity types; `investment_documents` similarly uses three plain nullable FKs (account/holding/valuation-snapshot) rather than `attachments`' pattern, for the same reason (a small, known-up-front set of link targets, not an open-ended one).
3. **Resolved**: `people` is the answer — a household member without a login is a `people` row with `user_id is null`; `financial_accounts.owner_person_id` and `transactions.related_person_id` both reference `people`, not `auth.users`/`household_memberships`, so ownership/attribution works identically whether or not the person has signed in.
