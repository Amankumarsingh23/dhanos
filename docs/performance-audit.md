# DhanOS — Performance Audit (PROMPT 47)

Status: **complete for this pass**. A dedicated performance/scale audit of the ten named data-access areas, run against real, purpose-built bulk data (not the tiny hand-written e2e fixtures already in the local dev database) and verified with live `EXPLAIN ANALYZE` output, not estimated.

**Read this section before any other claim in this document.** This review does not claim every corner of the codebase was load-tested. What it does claim, specifically:

- A dedicated household (`Perf Audit Household`, id `99999999-9999-4999-8999-999999999999`) was seeded at the volumes this prompt names — see §1 — via SQL scripts now committed at [`supabase/perf-seed/`](../supabase/perf-seed/) so this audit is reproducible on demand.
- The `transactions` and `activity_events` tables were additionally inflated to **125,000+ rows across 60 synthetic households** (`supabase/perf-seed/02_cross_tenant_noise.sql`) specifically so that index-vs-seq-scan planner decisions would be measured at realistic multi-tenant SaaS scale, not on a table so small that every plan is fast regardless of which index (if any) gets used.
- Every query plan cited below is a real `EXPLAIN ANALYZE` run against the local Postgres instance (`supabase status` was already running), not a prediction from reading the schema.
- Three real, confirmed bugs were found this way and fixed, tested, and re-verified live in this pass (see §4). Several more of the same *class* of bug were found and are disclosed, not fixed, in §5 — naming exactly why each was deprioritized.
- What this review is **not**: an exhaustive rewrite of every query in the app, a load test under concurrent traffic, or a production APM trace. Treat the findings below as **real, evidence-backed measurements at the volumes this prompt named**, not a certification that every code path is optimal at arbitrary scale.

## 4. Bugs found and fixed in this pass

All three were found by reading the actual query code (not just plan output) and confirmed with a real, live reproduction before being fixed — then re-verified live after the fix, plus the full unit suite.

### 4.1 Net-worth / dashboard / reports: `{ pageSize: 100 }` silently truncates past 100 rows

**The bug**: `getCurrentNetWorthBreakdown`, `getAvailableBalance`, and four report functions each fetched *a single page* of accounts/assets/lendings/liabilities/policies/SIPs/goals at `pageSize: 100` (or `MAX_PAGE_SIZE`) and never checked `hasMore` or fetched a second page. **Confirmed live**: with 150 real seeded accounts, `listAccounts(..., { pageSize: 100 })` returned exactly 100 — silently dropping 50, with zero indication anything was missing (unlike the already-existing, correctly-disclosed `currencyMismatchExcludedCount`).

**The fix**: added `fetchAllRows()` (`src/lib/queries/pagination.ts`) — pages through a `listX`-shaped function until `hasMore: false` or a safety cap of 50 pages (5,000 rows, far beyond any realistic per-household entity count), returning `{ rows, truncated }`. Applied to:
- `src/features/net-worth/queries.ts` — accounts, assets, lendings, liabilities. Added a new `truncated: boolean` field to `NetWorthBreakdown`, surfaced as a visible banner on the net-worth dashboard (`net-worth-dashboard.tsx`) in the rare case the safety cap is actually hit — the same disclosure pattern already used for `currencyMismatchExcludedCount`/`missingValuationCount`.
- `src/features/dashboard/queries.ts` — `getAvailableBalance`.
- `src/features/reports/queries.ts` — SIP consistency, insurance coverage, lending exposure, goal readiness reports.

**Verified live** (not just by reading code): a standalone script called the real `listAccounts` pagination contract against the real seeded household — old single-page approach saw 100/150 accounts; the new `fetchAllRows`-based approach saw 150/150 with `truncated: false`. Three new unit tests added (`src/lib/queries/pagination.test.ts`): fewer-than-one-page, the exact 150-row net-worth case, and the safety-cap case. Full suite: **780/780 unit tests pass** (777 before this pass + 3 new).

### 4.2 Staking daily-value series: silent PostgREST truncation + O(days × history) loop

**Bug (a) — correctness, not just performance**: `getDailyValueSeries`'s snapshot fetch (`src/features/staking/queries.ts`) had no `.range()`. PostgREST's own `max_rows = 1000` (`supabase/config.toml`) silently caps any such query — confirmed live: with 5,475 real snapshots seeded (5 positions × ~3 years), the query returned only the **oldest 1,000 rows**, spanning 2023-01-02 to 2023-07-20 only. A "trailing `daysBack` days ending today" chart built from this data would show a series that never reaches anywhere near today for any household with more staking history than ~1,000 total rows.

**Bug (b) — performance**: even once fetched correctly, the cumulative contributed/reward/withdrawal sums re-scanned each position's *entire* snapshot history from the start, for every single day in the requested window — O(days × total history per position).

**The fix**:
- (a) Explicit `.range()`-based pagination loop (page size 1,000, matching PostgREST's own cap; capped at 50 pages = 50,000 rows, with a deterministic `snapshot_date, staking_position_id` tiebreaker order for stable page boundaries).
- (b) Running per-position cumulative pointers (`cumulativeContributedByPosition`/`...RewardsByPosition`/`...WithdrawalsByPosition`), the same technique the existing `lastKnownClosing` pointer already used — O(days + total history) instead.

**Verified live**: the corrected paginated fetch now retrieves all 5,475 rows, reaching 2025-12-31 (the seed's actual latest date). A reference re-implementation of the *original* algorithm and the *fixed* pointer-based algorithm, run against the same correctly-fetched full dataset, produce **byte-identical output**; the fixed version measured **11.66ms → 0.88ms** (90-day window) and **25.60ms → 0.70ms** (366-day window) — a ~15–35× improvement at this seeded volume.

### 4.3 CSV import: N+1 `import_rows` status updates after each chunk

**The bug**: `commitChunk()` (`src/features/imports/actions.ts`) batches the actual data insert (200 rows per chunk, already correct), but then updated each row's `import_rows.status`/`error_message`/`created_entity_id` with its *own individual* `.update().eq("id", rowId)` call — up to 200 separate round-trips per chunk, across two loops (rejected rows, then imported rows) — because each row's values differ and a single blanket `.update()` can't express that.

**The fix**: a new Postgres RPC, `bulk_update_import_row_status(p_updates jsonb)` (`supabase/migrations/20260730100000_bulk_update_import_row_status.sql`), does one `UPDATE ... FROM jsonb_to_recordset(...)` statement per chunk instead. **`SECURITY INVOKER`** (not `DEFINER`) — runs as the calling user so the existing "owners, admins, and editors can update import rows" RLS policy still applies exactly as it did to the individual updates it replaces (see `docs/data-access-patterns.md` §1.1's atomic-multi-row-write pattern, same convention as the app's other RPCs).

**Verified live**: applied the migration to the local database, regenerated `src/types/database.ts`, then called the real RPC via `supabase-js` with 3 rows carrying 3 different status/value combinations (one rejected with an error message, two imported with different `created_entity_id`s) in a single round-trip — confirmed all 3 rows updated correctly with their distinct values. Full suite still **780/780**; `pnpm typecheck` clean.

## 5. Same-class bugs found but *not* fixed in this pass — named honestly

Per this prompt's own instruction not to overclaim, these are real findings of the same defect class as §4, deliberately left unfixed here because they fall outside this prompt's explicitly named areas (dashboard, net-worth, reports, charts, CSV import) or are safe at the volumes this prompt actually names:

- **The same `{ pageSize: 100 }` / `{ pageSize: MAX_PAGE_SIZE }`-no-loop pattern exists in ~15 more call sites**: staking's own positions list (inside `getDailyValueSeries`), insurance's dashboard queries, goals, lending's dashboard queries, loans' debt summary, monthly-closing, recurring rules, investment-SIPs, emergency-fund, and money-drains queries. Same class of bug as §4.1; not audited/fixed here since none of those modules is one of this prompt's ten named areas.
- **`fetchPortfolioData`** (`src/features/investments/queries.ts`, backing portfolio charts and `getPortfolioHoldings`) fetches *all* `investment_transactions` and *all* `investment_valuation_snapshots` for a household with no date bound and no `.range()`. Safe at the volumes this prompt names (360 + 300 rows seeded, both well under PostgREST's 1,000-row cap) — but shares the exact same latent silent-truncation risk as the staking bug (§4.2a) once a household's investment history grows past ~1,000 total rows (plausible for a long-lived household with many holdings and years of SIPs).
- **`getAccountBalanceTrend`** (dashboard) fetches all active base-currency accounts with no `.range()` — safe within this prompt's own "hundreds of accounts" volume (150 seeded, confirmed under the 1,000-row cap) but the same latent-risk class.
- **CSV import duplicate-candidate queries** (`getTransactionDuplicateCandidates` etc.) fetch a whole account's non-cancelled transaction history with no date bound — bounded in practice by one account's real history, not fixed here.
- **`getDocumentsOverview`**'s status/size/expiry counts are read from a single `.limit(100)` page — undercounts past 100 documents. Lower priority: documents aren't named at "hundreds+" volume in this prompt's test-volume list.
- **No new composite index** was added for `transactions(household_id, kind, status, transaction_date)`. Measured need at the volumes actually audited was negligible — the dashboard's cash-flow-by-kind sum query ran in **1.046ms** via the existing single-column `transactions_household_id_idx` alone, even at 125,227 total table rows. This is a plausible *future* scaling knob if a single household's transaction count grows into the tens of thousands, not a currently-measured problem.
- **Recurring-rule generation**'s outer "which rules are due" fetch (§2 #8) was not stress-tested with hundreds of simultaneously-overdue rules in one household.

## 6. Caching

**No query-result caching layer exists anywhere in this app** — confirmed by grep: zero uses of `unstable_cache`, zero uses of `revalidateTag`, zero raw `fetch()` calls with Next.js cache directives, zero module-level/in-memory caches in `src/lib`. `revalidatePath` (176 call sites) exists but is the App Router's own render-cache invalidation, not a data cache with a shareable key.

This means the acceptance criterion **"no household data enters public cache"** is trivially satisfied today — there is no cache of any kind for household data to enter. It also means **"safe household-specific caching" is not yet a built capability** — there is nothing to audit for cache-key safety because nothing is cached. Every Server Component/Server Action reads Supabase live, per request, under RLS. Disclosed honestly rather than claimed as "done": if a caching layer is added later, every query in this codebase is a green-field candidate, and any such addition must key on household id *and* verified membership (per `docs/data-access-patterns.md` §2's existing "free of cross-user caching" rule) before it ships.

## 10. Summary
